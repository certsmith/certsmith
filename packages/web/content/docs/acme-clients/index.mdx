## Client Compatibility Matrix

| Client | Protocols / Challenges | Trust Anchor Requirement | Best Suited For |
| :--- | :--- | :--- | :--- |
| **Certbot** | HTTP-01, DNS-01, Standalone | System Trust Store / `REQUESTS_CA_BUNDLE` | Linux hosts, Apache, standalone VMs |
| **Lego** | HTTP-01, DNS-01 (100+ DNS providers) | `--ca-certificates` flag | Go automation, CLI tooling, multi-DNS scripts |
| **acme.sh** | HTTP-01, DNS-01, Stateless | `--ca-bundle` flag | Minimal environments, routers, OpenWrt, BSD |
| **Caddy** | HTTP-01, TLS-ALPN-01, Internal | `ca_root` in Caddyfile | Reverse proxy with zero-config auto-renewals |
| **Traefik** | HTTP-01, TLS-ALPN-01 | `rootCAs` in static configuration | Docker Swarm, microservices, container ingress |
| **cert-manager**| HTTP-01, DNS-01 | `caBundle` in `ClusterIssuer` spec | Kubernetes clusters, ingress controllers, mTLS |

## Universal Prerequisites for ACME Clients

1. **Root CA Trust**: Because CertSmith uses a private Root CA, your ACME client needs to trust the CertSmith Root CA. This can be accomplished either by installing the root certificate into the operating system trust store or passing the certificate path directly to the client's CA bundle configuration option.
2. **Network Reachability**: The client must be able to reach CertSmith's port 443 (HTTPS) to fetch directory endpoints and place orders.
3. **Challenge Validation**: CertSmith must be able to validate your chosen challenge (e.g., reaching port 80 on your client for `HTTP-01`, or resolving TXT records via DNS for `DNS-01`).
